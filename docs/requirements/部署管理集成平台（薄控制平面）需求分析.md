# 部署管理集成平台（薄控制平面）需求分析

> 目标：做一个“薄控制平面”，统一入口给管理员进行应用与环境的部署/回滚/审批/可视化；**不自研 CD 引擎**，所有执行动作落在 Git 与现成编排/发布系统（Argo CD / Argo Rollouts / Airflow/Argo Workflows / Helm / Terraform）。平台只做编排、授权、审计与状态聚合。

---

## 1. 背景与问题
- 当前后端为 Spring Boot API 查询服务 + 大数据平台（多任务 SQL 抽取/执行），年数据量 ~200 亿行。
- 团队规模 5–6 人，发布频率高峰期日更、平时周更两次；主要风险是**回滚慢**与**数据作业误伤**。
- 现有工具分散（Git、制品仓、Argo/Airflow、观测），管理员缺少统一入口与可审计的端到端流程。

## 2. 目标（Goals）
- **统一入口**：按“应用 × 环境”维度，集中操作发布/回滚、查看状态、导出审计。
- **标准化发布**：所有变更生成 PR（只改镜像 tag/Helm values/IaC 变量），合并后由 Argo/Airflow 等执行。
- **可靠回滚**：一键 Revert 最近发布，1 分钟内完成服务回退；数据作业回滚到上个版本。
- **灰度与门禁**：集成 Argo Rollouts 金丝雀（5%→25%→50%→100%），基于 Prometheus 指标自动/人工推进与回滚。
- **数据安全**：数据作业先影子/采样跑 + 校验（行数/哈希/聚合），不通过不放量。
- **强审计**：所有操作均可追溯至 Git/Argo/Airflow 记录，导出发布材料包。
- **密钥最小化暴露**：不存明文密钥，仅展示 Secret 引用；OIDC 短期令牌换取下游访问。

## 3. 非目标（Non-Goals）
- 不自研部署/调度引擎（不重造 Argo/CD、Airflow、K8s）。
- 不在平台内长期保存云凭证、数据库密码等敏感值。
- 不暴露“直接 kubectl”或数据库直连操作入口。

## 4. 术语
- **GitOps**：以 Git 为期望态，集群自动对齐现实态（Argo CD/Flux）。
- **金丝雀发布**：小流量逐步放量，结合指标门禁自动回滚。
- **影子/采样跑**：对数据作业，先在影子表或 1–5% 样本跑，校验通过再跑全量。

## 5. 角色与权限模型
角色：
- **Admin**：系统与策略管理、应用/环境注册、紧急回滚。
- **Operator**：在授权范围内发版/回滚、查看状态、导出报告。
- **Approver**：审批 PR（人/组），平台校验是否满足策略。
- **Viewer**：只读看板与审计。
- **DataOps**：数据作业发布与校验管理。

权限矩阵（摘要）：
| 功能 | Admin | Operator | Approver | Viewer | DataOps |
|---|---|---|---|---|---|
| 应用/环境注册 | ✓ | – | – | – | – |
| 发版/回滚（应用） | ✓ | ✓ | – | – | – |
| 发版/回滚（数据作业） | ✓ | – | – | – | ✓ |
| 审批策略配置 | ✓ | – | – | – | – |
| 查看状态/审计 | ✓ | ✓ | ✓ | ✓ | ✓ |
| 变更冻结窗口 | ✓ | – | – | – | – |

> 细粒度授权到“应用 × 环境”，RBAC 依赖 OIDC/SSO 组映射。

## 6. 关键用例（User Stories）
- **UC-01 发版应用**：选择应用/环境/版本 → 创建 PR（仅改镜像 tag/Chart 版本）→ 审批 → 合并 → Argo CD 同步 → Argo Rollouts 金丝雀 → 门禁通过自动全量，否则自动回滚。
- **UC-02 一键回滚**：选择应用/环境 → 选择目标版本 → 生成 Revert PR → 合并 → 自动回退。
- **UC-03 数据作业变更**：选择作业版本 → 影子/采样跑 → 数据校验通过 → 触发全量；失败自动回滚。
- **UC-04 审批与冻结**：平台校验 PR 是否满足审批人/窗口策略；冻结期禁止合并（含例外白名单）。
- **UC-05 可观察性看板**：聚合错误率、延迟、吞吐、5xx、关键交易失败率与 Airflow 任务成功率。
- **UC-06 审计导出**：导出单次发布的材料包（变更 diff、构建信息、放量轨迹、指标曲线、数据校验报告）。

## 7. 业务规则
- **所有变更必须是 PR**，平台不直接写集群；合并即代表发布授权。
- **默认发布策略**：金丝雀 5%→25%→50%→100%，每步 10 分钟；门禁：`error_rate < 1%` 且 `p95 <= 基线 × 1.2`，否则自动回滚。
- **数据库变更**：遵循 Expand/Contract，两阶段上线；DDL 走 Online（gh-ost/PT-OSC/Online DDL）。
- **数据作业**：`max_active_runs=1` 禁止并发；幂等写入（MERGE/UPSERT）；失败指数退避重试 + 断点续跑。
- **密钥**：仅展示 Secret 引用名（External Secrets / KMS/SSM），平台不存密文。

## 8. 端到端流程
### 8.1 应用发布（Web → PR → Rollouts）
1. 选应用/环境/版本（镜像 tag 或 Chart 版本）。
2. 平台创建 PR（更新 `env/<env>/<app>.values.yaml` 中镜像 tag）。
3. CI 校验（Lint/Policy/SBOM/签名验证）。
4. 审批合并 → Argo CD 同步到目标环境。
5. Argo Rollouts 启动金丝雀：5%→25%→50%→100%，每阶段检查门禁（Prometheus 指标）。
6. 失败即自动回滚；成功则记账并生成材料包。

### 8.2 应用回滚
1. 选择历史发布（Release）。
2. 一键生成 Revert PR 并合并。
3. Argo CD 同步回退；Rollouts 关闭新版本副本。

### 8.3 数据作业变更
1. 选作业/版本。
2. 触发影子/采样运行（1–5% 或影子表 `*_shadow`）。
3. 校验（行数/哈希/聚合 diff、阈值可配置）。
4. 通过则触发全量；失败则自动回滚到上版本；保留 `t+1` 快照 2–3 天。

## 9. 架构设计
**前端**：React，界面：应用/环境目录、发布与回滚向导、状态看板、审计导出。

**后端（Spring Boot）**：编排网关，统一鉴权/RBAC，调用下游 API。

**集成器**：
- Git 提供商 API（GitHub/GitLab）：创建/合并 PR、Webhook 回调。
- Argo CD API：应用状态、同步、Diff。
- Argo Rollouts + Prometheus：阶段进度与门禁结果。
- Airflow/Argo Workflows：触发影子/全量作业、读取运行结果。
- Artifact 仓库（Harbor/ECR/ACR）：镜像版本列表与签名校验。
- 身份：OIDC/SSO（OAuth2/OIDC 码流），获取组用于 RBAC。

**存储**：Postgres（只存元数据映射、审计副本与策略；不存密钥）。

**可观测性**：OpenTelemetry/Micrometer → Prometheus（Metrics）、Loki/ELK（Logs）、Grafana（Dashboards/Alerts）。

## 10. 外部接口（API 草案）
- `POST /api/releases`：创建发布（生成 PR）。
- `POST /api/releases/{id}/rollback`：回滚。
- `GET /api/apps` / `GET /api/environments`：查询目录。
- `GET /api/deployments?app=&env=`：查询部署状态（汇聚 Argo/Prometheus）。
- `POST /api/data-jobs/{id}:runShadow`：触发影子/采样运行。
- `POST /api/data-jobs/{id}:promote`：影子通过后升级为全量。
- `GET /api/audits/{releaseId}`：导出发布材料包。

**Webhooks**：
- `/webhooks/git`：PR 状态、合并事件。
- `/webhooks/argo`：同步/健康变更。
- `/webhooks/airflow`：任务运行完成/失败。

## 12. 安全与合规
- OIDC/SSO，后端按短期令牌代表用户调用下游 API；**禁用长 Token**。
- 密钥管理走 External Secrets + 云 KMS/SSM，平台仅展示引用名。
- 策略执行：OPA/Gatekeeper/Conftest 对 Helm/IaC 变更做策略校验（审批人、窗口、标签、资源配额、命名规范）。
- 审计：所有变更与执行均有可追溯记录，导出压缩包用于审计留档。

## 13. 发布策略与门禁（默认）
- **金丝雀**：`5% → 25% → 50% → 100%`，每步 `10m`。
- **指标阈值**：
  - 错误率 `< 1%`
  - p95 延迟 `<= 基线 × 1.2`
  - 关键交易失败率不升高（自定义 PromQL）。
- **自动回滚**：任一阈值越界，平台触发 Rollouts 回退并生成告警与审计条目。

## 14. 运维与可观测性
- 看板：应用 SLA、p95、错误率、吞吐、5xx；数据作业成功率、时延、重试。
- 告警：5 分钟内同类型告警 ≥ 3 次 → 自动回滚。
- 指标基线：以近 7 天同时间段作为对比基线。

## 15. 非功能性需求（NFR）
- **可用性**：平台自身 99.9%，不影响下游系统可用。
- **性能**：目录/状态查询 P95 < 500 ms；审计导出 ≤ 30 s（异步）。
- **扩展性**：应用 200+、环境 10+ 时仍稳定；水平扩容后端与前端。
- **可靠性**：回滚 RTO ≤ 1 分钟；发布 MTTR ≤ 15 分钟。
- **安全**：不落地密文；字段级审计；最小权限访问下游。

## 16. MVP 范围与里程碑
- **M0 基线**：打通 OIDC、Git PR 创建/合并、Argo CD 同步状态回流。
- **M1 MVP**：
  - 应用/环境目录；一键发布/回滚（PR 驱动）。
  - 金丝雀固定 5/25/50/100，Prometheus 门禁与自动回滚。
  - 审计材料包导出（变更 diff + 指标截图/链接）。
- **M2**：审批策略（必需审批人/组、冻结窗口管理）；Artifact 仓镜像签名与 SBOM 校验。
- **M3**：数据作业影子/采样 + 校验集成（Airflow/Argo Workflows）。
- **M4**：策略商店（OPA 模板）、多集群/多租户、报表化发布统计（DORA 指标）。

## 17. 风险与对策
- **认证/授权复杂**：先以“应用 × 环境”粗粒度落地，后补细粒度动作级授权。
- **API 配额限制**：启用缓存与 Webhook 驱动，降低轮询频率。
- **漂移**：Argo Diff 与告警；禁止绕过 PR 的直接改动（合规策略）。
- **指标门禁误伤**：提供“人工越权放量”但必须留痕并注明理由。
- **数据回滚复杂**：强制日快照 2–3 天；影子/采样覆盖关键链路。

## 18. 验收标准（Success Criteria）
- 回滚时间 ≤ 1 分钟；发布失败自动回滚成功率 ≥ 99%。
- 审计材料包覆盖 100% 发布；可在 1 分钟内检索到任一发布的完整链路。
- 数据作业影子/采样覆盖率 ≥ 90%，校验失败能自动拦截全量。
- 无明文密钥在平台存储与日志中出现。

## 19. 附录
### 19.1 目录约定（示例）
```
repo/
  charts/<app>/Chart.yaml
  env/
    staging/<app>.values.yaml
    prod/<app>.values.yaml
  data-jobs/
    jobA/
      job.yaml   # 参数、调度、输出
      sql/
        step1.sql
        step2.sql
```

### 19.2 Expand/Contract 变更清单（数据库）
- Expand：新增列/影子表、双写或影子写、回读校验。
- 切换：应用读路径切向新列/表，保持旧路径可读。
- Contract：稳定后删除旧列/表与写入逻辑。

### 19.3 Runbook（应急）
1. 一键回滚（Revert PR）并确认 Argo 同步完成。
2. 打开限流/熔断开关，观察 10 分钟。
3. 若涉及数据：回切到 `t-1` 快照或影子表，触发补偿任务。
4. 复盘：生成事件报告并归档到审计库。

---

**结论**：平台聚焦“把 Git 与 CD/工作流串起来”，把回滚、审计、灰度与数据校验做成体系，克制范围即可在小团队内稳定落地。
