# 部署管理薄控制平面设计文档

## 1. 概览
- 平台定位为“薄控制平面”，聚焦在统一入口下的部署、回滚、审批、审计与观测编排，实际执行仍委托给现有 GitOps/CD/工作流体系（Git、Argo CD、Argo Rollouts、Airflow、Helm、Terraform）。
- 前端采用 React 微前端方式嵌入主应用管理控制台，复用主应用导航、样式与会话；后端基于 Spring Boot，负责身份鉴权、策略校验、发布编排与数据聚合。
- 持久化使用 Postgres 存储元数据与审计记录，审计材料包落地对象存储；Prometheus/Grafana/Loki 负责指标、看板与日志，所有告警与审计事件同步到主应用。
- 核心价值包括：PR 驱动的标准化发布、Prometheus 指标守门的金丝雀策略、数据作业影子/采样验证、最小化密钥暴露以及管理员能力集中到主应用。

## 2. 范围与约束
- **范围内**：应用/环境目录维护、发版与回滚流程、金丝雀策略与门禁、数据作业灰度、审批及冻结策略、审计材料导出、观测信息聚合、与主应用管理员功能融合。
- **范围外**：自研部署/调度引擎、保存明文密钥、提供直接 kubectl/数据库入口、取代现有 CI/CD 管道。
- **约束条件**：沿用主应用 OIDC/SSO，遵守现有仓库结构（charts/env/data-jobs），受制于 Git/Argo/Airflow API 配额，需要适配主应用的角色体系与审计规范。

## 3. 角色与权限
- **Admin**：环境注册、策略管理、紧急回滚、越权放量。
- **Operator**：在授权范围内发版、回滚、查看状态、导出审计。
- **Approver**：审核发布 PR，确保策略满足。
- **DataOps**：负责数据作业影子跑、校验、放量。
- **Viewer**：只读查看看板与审计。
- **主应用管理员**：在统一后台中调用部署平台 API，查看合并后的审计、告警与状态。
- 权限粒度遵循“应用 × 环境 × 动作”，部署平台从主应用同步角色映射，运行时按 token claims 校验。

## 4. 核心用例
1. **应用发版**：选择版本 → 生成 PR → CI 校验 → 审批合并 → Argo CD 同步 → Argo Rollouts 金丝雀 → Prometheus 门禁 → 自动放量或回滚 → 审计。
2. **一键回滚**：选择历史 Release → 生成 Revert PR → 合并 → 恢复旧版本 → 更新审计与告警。
3. **数据作业灰度**：触发影子/采样运行 → 校验行数/哈希/聚合 → 通过则全量，失败自动回滚并出具报告。
4. **审批与冻结**：校验 PR 是否满足审批人、冻结窗口；支持带审计的人工越权。
5. **观测看板**：聚合错误率、延迟、吞吐、5xx、数据作业成功率等指标，并嵌入主应用仪表盘。
6. **审计导出**：生成包含 diff、构建信息、放量轨迹、指标曲线、校验报告的材料包供下载与归档。
7. **主应用集成**：微前端在主应用导航中加载，与管理员功能整合，复用单点登录、审计中心、告警通道。

## 5. 架构总览
- **前端**：React 微前端（模块联邦或 iframe），暴露发布向导、灰度监控、策略配置、审计列表。通过 postMessage 或共享存储与主应用交换短期访问凭据，并支持 BroadcastChannel 处理续期与登出。
- **后端**：Spring Boot 服务，分为 API Gateway、领域服务、集成适配器。结合主应用的 BFF 模式，由 BFF 持有 Access/Refresh Token 并代表前端完成 on-behalf-of 换取，部署平台后端仅接受短期会话或一次性 token。
- **存储层**：Postgres（元数据、策略、审计），对象存储（审计材料包），缓存（Redis/内存）加速状态查询与限流。
- **外部集成**：
  - Git Provider：PR CRUD、Webhook 回调、签名校验。
  - Argo CD / Argo Rollouts：同步、Diff、金丝雀推进/回滚。
  - Argo Workflows / Airflow：触发 CI/CD 流水线与数据作业，获取运行状态。
  - Artifact 仓库：镜像版本、签名、SBOM 校验。
  - Prometheus/Grafana：指标查询、仪表盘链接。
  - 主应用：角色同步、审计事件、告警推送、导航壳体。
- **事件流**：统一 Webhook 接口写入队列（Kafka/RabbitMQ/本地事件总线），异步更新状态与审计。
- **运维体系**：Prometheus 指标、Loki/ELK 日志、Alertmanager 告警统一归入主应用运维面板。

## 6. 后端模块划分
- **Auth Gateway**：验签 OIDC token、实施 on-behalf-of 换取下游访问令牌、限流、打审计标识。
- **Directory Service**：管理应用/环境/数据作业目录，支持从 Git 结构导入与主应用角色映射缓存。
- **Release Orchestrator**：生成与更新 PR，跟踪 CI 状态，触发 Argo CD 同步，控制金丝雀阶段推进，处理人工越权与自动回滚。
- **Policy Engine**：审批人校验、冻结窗口、指标门禁、签名/SBOM 校验；对 Helm/IaC 变更调用 OPA/Conftest。
- **Data Job Orchestrator**：管理影子/采样运行，调用 Airflow/Argo Workflows，执行校验规则并决定是否放量。
- **Observability Aggregator**：封装 Prometheus、Argo Rollouts、Grafana，提供健康摘要给 UI 与主应用小部件。
- **Audit & Reporting**：记录全量审计事件，生成可下载材料包，向主应用审计中心推送。
- **Admin Integration Adapter**：暴露角色同步 API，回推告警与审计事件，支撑主应用对紧急操作的统一控制。

## 7. 数据模型（节选）
```
application(id, name, repo_url, chart_path, owners, health_checks, created_at)
environment(id, name, git_path, cluster_ref, namespace, config_json)
release(id, application_id, target_env_id, version, commit_sha, created_by, status, started_at, finished_at)

canary_policy(id, application_id, stages_json, step_interval_minutes, gates_json, allow_manual_override)

```

## 8. 接口设计
- `POST /api/releases`：创建发布、生成 PR、执行策略校验。
- `POST /api/releases/{id}/advance`：推进金丝雀阶段或提交人工越权。
- `POST /api/releases/{id}/rollback`：指定版本回滚。
- `GET /api/deployments`：按应用/环境聚合部署状态与指标摘要。
- `POST /api/data-jobs/{id}/shadow-run`：触发影子/样本运行。
- `POST /api/data-jobs/{id}/promote`：影子运行转全量。
- `GET /api/policies` / `POST /api/policies/validate`：策略查询与预校验。
- `GET /api/audits/{releaseId}`：获取审计材料包下载链接。
- `POST /api/admin/roles/sync`：接收主应用角色映射。
- `POST /api/admin/events`：主应用上报越权或紧急操作结果。
- Webhooks：`/webhooks/git`、`/webhooks/argo`、`/webhooks/airflow` 验证签名后写入队列。

## 9. 核心流程
- **应用发布**：前端发起 → Policy Engine 校验 → PR 创建 → CI 回调 → Approver 合并 → Argo CD 同步 → Rollouts 阶段推进 → Prometheus 守门 → 成功/回滚 → 审计写入 → 主应用审计更新。
- **持续集成**：代码提交 → Argo Workflows 触发构建/测试/镜像推送 → 输出制品与 SBOM → 生成或更新 Git PR（镜像 tag/Helm values）→ 部署管理平台接管后续审批与发布。
- **历史回滚**：选择 release → 生成 Revert PR → 合并 → Argo 同步旧版本 → Rollouts 停止新版本 → 触发告警与审计。
- **数据作业放量**：影子运行 → 校验指标（行数/哈希/聚合）→ 通过则调用 Promote → Airflow/Argo Workflows 全量 → 审计归档；失败自动回滚并下发报告。
- **主应用集成**：管理员登录主应用 → 加载微前端 → 主应用通过安全信道传递 token → 统一导航触发操作 → 部署平台返回结果与事件 → 主应用事件中心展示。

## 10. 安全设计
- OIDC PKCE 登录由主应用处理，Access Token 生命周期 < 1 小时；主应用 BFF 持有 Refresh Token 并代表前端换取短期访问令牌，部署平台后端仅依赖短期 token 或服务间信任。
- 前端与微前端之间使用 postMessage + nonce 或共享 store 传递一次性 token，并通过 BroadcastChannel 广播续期/登出事件；微前端仅在内存中保存 token。
- RBAC 以“应用 × 环境 × 动作”为粒度，部署平台定时从主应用同步角色-权限映射并缓存。
- 密钥最小暴露：仅展示 External Secrets/KMS/SSM 引用名，日志与审计脱敏处理。
- 关键动作（越权放量、紧急回滚、策略变更）要求二次确认与多因子校验，并生成具备签名的审计事件。
- Webhook 验签、防重放、限流；外部调用失败采用指数退避并记录告警。

## 11. 可观测性
- **指标**：API 延迟、错误率、外部 API 时延、金丝雀阶段耗时、回滚成功率、影子校验失败率。
- **日志**：结构化 JSON，包含 trace_id、release_id、actor，敏感信息脱敏。
- **告警**：API 错误激增、外部集成失败、指标门禁触发、审计导出失败，统一上报主应用 Alertmanager。
- **审计**：所有操作留痕，支持过滤、导出、与主应用审计中心对齐字段。
- **CI/CD 观测**：收敛 Argo Workflows、Argo Rollouts 指标（构建耗时、失败率、阶段状态）、制品推送结果，纳入主应用仪表盘与告警策略。

## 12. 非功能要求
- 平台可用性 ≥99.9%，目录/状态查询 p95 < 500ms，审计包生成 ≤30s（异步）。
- 支撑 ≥200 个应用、≥10 个环境、50 并发管理操作，后端与前端可水平扩容。
- 回滚 RTO ≤1 分钟；发布失败自动回滚成功率 ≥99%。
- 数据安全：字段级审计、配置加密、无明文密钥写盘或入日志。

## 13. 部署与运维
- 使用 `./mvnw.cmd clean verify` 构建，输出 Docker 镜像，借助 Argo CD + Helm 部署；平台自身用 Argo Rollouts 实施金丝雀。
- 配置管理：`application.yml` + profile；敏感值通过 KMS 注入；支持多环境（dev/prod/offline）。
- 测试策略：JUnit5 单元/集成测试，Mock Git/Argo/Airflow；Prometheus 查询模拟；端到端场景自动化脚本。
- Runbook：紧急回滚、外部依赖熔断、策略失效处理、消息堆积清理、主应用失败时的独立入口切换。

## 14. 迭代路线
1. **M0 基线**：打通 SSO、目录浏览、PR 创建、Argo 状态回流；主应用导航初步集成。
2. **M1 MVP**：固定金丝雀策略、Prometheus 门禁、自动回滚、审计材料导出；主应用 SSO/菜单完全整合；Argo Workflows 承载基础 CI 流水线。
3. **M2**：审批与冻结策略、镜像签名 + SBOM 校验、角色同步、联合审计展示；BFF token 模式在部署管理模块落地。
4. **M3**：数据作业影子验证、Airflow/Argo Workflows 深度集成、指标报表；主应用管理员仪表盘增强，纳入 CI/CD 指标。
5. **M4**：策略模板商店、多集群/多租户、DORA 指标报表、主应用运维面板全量融合，并全面迁移旧模块至 BFF/token 体系。

## 15. 风险与对策
- 外部 API 配额：优先使用 Webhook，状态缓存与限流，必要时与主应用协商服务账号配额。
- 授权复杂：先上线粗粒度权限，再逐步细化；提供权限可视化与模拟工具。
- 指标误判：阈值可配置、设定死区、结合历史基线，支持带理由的人工越权。
- 数据回滚难：强制影子/采样覆盖关键链路，保留日快照 2–3 天，提供补偿任务模板。
- 集成耦合：微前端契约测试与版本协商，保留独立访问入口作为退路，主应用异常时可降级为只读模式。
- Token 管理：推行 BFF + 短期 token 模式，统一续期/吊销广播；在迁移期设置监控防止 token 泄露或过期导致操作失败。

## 16. 待确认事项
- 主应用与微前端间的 Token 传递方式（postMessage + nonce、共享状态 or BFF 转发）的最终选型与安全校验、握手流程。
- 审计材料包存储选型（内部对象存储或主应用既有方案）与保留周期要求。
- 是否需要支持 Terraform/IaC 以外的自定义脚本适配及相应策略检查。
- 主应用事件中心对高频部署事件的吞吐能力，是否需引入队列缓冲层。

## 17. React 迁移方案
- **目标**：将部署管理模块及后续复杂前端能力迁移至 React 微前端，同时维持与主应用导航、鉴权、审计、运维的统一体验。
- **阶段规划**
  - *准备评估（0–2 周）*：确定 React 技术栈（React 18、Router、Query/Redux、CSS Modules 等）、梳理可复用资产、敲定微前端与 token/BFF 策略，形成《前端迁移蓝图》。
  - *基础设施搭建（3–4 周）*：创建 React 子项目、配置模块联邦/iframe 加载、建立共享组件库与 API 工具、落地 BFF 短期 token 传递及 BroadcastChannel 续期机制。
  - *核心功能迁移（5–9 周）*：重写发布向导、灰度监控、策略配置、审计列表、数据作业流程，联调后端接口，补充 React Testing Library/Playwright 测试并接入 CI。
  - *渐进推广（10–13 周）*：扩展至其他高复杂度模块，建设 Storybook/UI Catalog，更新开发规范并开展培训。
  - *收尾优化（14 周以后）*：清理遗留 DOM 脚本与垫片，完善 BFF token 运维方案，评估全站 SPA 化的下一阶段路线。
- **关键里程碑**：M1 微前端骨架+BFF token 试跑；M2 部署管理 React 版本灰度上线；M3 指标、审计、监控集成完成并拆除旧页面；M4 统一推广到其余模块。
- **风险缓解**：开展 React 培训与 code review checklist；严格使用 CSS Modules/命名空间防止样式冲突；feature flag 保留旧页面快速回退；灰度期监控性能与错误率。

- **BFF 接口**：新增 `/api/deploy-platform/token`，由 Spring Security 限制 `ADMIN/SUPER_ADMIN` 访问。服务端对前端随机 nonce 做一次性校验，签发短期 JWT（默认 30 分钟）返回 `accessToken`、`expiresAt` 等字段，并写入审计表 `deploy_token_audit`。重复或过期 nonce 返回 400，并记入审计。

- 管理控制台侧边栏新增“部署管理平台”菜单项（与“服务器群组管理”同级），点击后加载 `/admin/deploy-platform/content` 片段并自动挂载 React 微前端。
